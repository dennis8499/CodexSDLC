# 系統分析的做法

排做法時依序核對改動範圍、資料表、精度和測試工具，再按格式回傳。

## 改動範圍

使用者在 ③ 核准的「改動範圍」就是從你這裡謄過去的，`implementer` 拿它當邊界：**你沒列的既有檔，就是他沒批准過、卻會被改掉的那一處。**

- **既有行為會變的**（回傳的那一節）：照需求決議，現在的系統哪些行為會改 —— 改前（附 `path:line`，你開檔看過的）→ 改後，一項一行。這是需求層的，跟選哪個做法無關；只新增、既有行為都不變就寫「無」。
- **每個做法的「動到」分開寫「改」與「新增」**：改的是既有的檔、表、設定、SP；只加一行接線（DI 註冊、路由、DbContext 的 DbSet）也算改，照列。
- **連帶影響**：做法要改的每一個既有方法、SP、表或設定，查一次誰在用（`impact-scope.ps1` 帶它的名字，或 grep 一次）。呼叫端屬於別的功能 → 列進那個做法的「連帶影響」（功能 ＋ path）。**只查直接呼叫端**，不追第二層，寫明「只查了直接呼叫端」。
- **既有測試**：斷言了這次要改的行為、會要改期望值或刪掉的測試，列進「既有測試」（`path::名稱`；`.feature` 寫 scenario 標題）。不知道有沒有就寫查過什麼 —— 不要寫「無」。

## 資料表設計

做法會新增或修改資料表、欄位、索引、約束、view／SP／function，或在代碼表、存進 DB 的列舉加新的值 → **每個這種做法一節，寫進 `bdd-docs/{feature-id}/data-model.md`**，格式見 skill `er-modeling`。**`completed` 也寫**（跟 `analysis.md` 相反）：使用者在 ③ 確認的就是這份表格，`implementer` 照它建 —— 不寫成檔，資料表就是 ④ 的自由發揮，使用者要到交付才看得到。做法的「資料模型」那一行指到它那一節；都不動 schema 就不寫檔。

- **照這個 repo 的慣例設計**：命名、主鍵型別、稽核欄位、軟刪除、時間與金額型別、migration 工具與落點，取自既有的 migration／ORM model／`*.sql`，`guidelines/sql.md` 存在就照它（衝突以規範為準）。依據寫在那一節。
- **既有表的欄位定義檔案裡查不到**（DB-first、只有 live DB 看得到）→ 照角色的 live DB 規則回 `blocked`，指出要查的表與欄位定義。
- **業務上要決定的不替他定**（長度上限、能不能空、唯一性、保留多久）—— 需求決議沒談到的，表格裡標「待確認」，回傳另寫一條「需求缺口：」。
- **檔已經在**：spec.md 指到過的節是核准過的，原樣保留 —— 同一塊功能的下一次迭代在尾端接著寫（`## 迭代 N：A) …`）；沒被指到的節（中斷前寫的、上次沒被選的）改寫或刪掉。
- **上限約 150 行。** 超過 → 建議做法那一節寫全，其餘會動 schema 的做法只寫「新增／修改哪幾張表」一行，回傳「沒做完」寫明哪幾個做法只寫了表名 —— 使用者選了它，orchestrator 會叫你補。

## 精度

`spec.md` 已經談定「捨到第幾位、在哪一步捨、哪個方向、負數怎麼算」。**那是 ① 的業務決策，不歸你動。你查的是系統做不做得到：**

- 相關欄位的**實際型別與 scale** —— `decimal(18,2)`？`float`／`real`？SQL Server 的 `money`（只有 4 位，且乘除有已知誤差）？
- 現有程式碼**用哪個捨入 API**。C# `Math.Round` 不帶 `MidpointRounding` 時**預設是銀行家捨入**，而寫的人幾乎都以為是四捨五入 —— 看到沒帶參數的呼叫，那就是現況，照實寫，不要當成筆誤。
- **上下游的精度**：對外 API 的 JSON number 是 IEEE754 double，存不住 `0.1`；報表、發票、金流閘道各有各的位數。
- 既有資料裡**有沒有已經不符合新規則的** —— 那一條直接餵給交付前的不可逆性判斷。

每個做法多一行：

```text
- 精度：{欄位型別與 scale} | 與 spec 談定的一致 | 衝突：{具體是哪裡對不上}
```

**衝突要在 ③ 之前攤開。** spec 談定「捨到厘（4 位）」而欄位是 `decimal(18,2)`，或程式現在走的是銀行家而 spec 寫四捨五入 —— 使用者在 ③ 下的是**不可逆**的決定，這種對不上的事不能留到 ④ 才發現。

`spec.md` 沒談到精度、需求裡也沒有會被計算的數 → 那一行寫「**精度：無**」**就結束**。不要自己去翻資料庫找數字欄位 —— 那是沒有終止條件的掃描。

## BDD 測試工具

`index-digest.json` 的 `test-toolchain.bdd` 是空的 → **每個做法的「動到」都多列一項**：測試專案，加上 `bdd-fallback` 那個套件（例：`Orders.Tests.csproj`（加 `Reqnroll.NUnit`））。前端看 `node-packages` 裡那個套件自己的 `test-toolchain`：`bdd-fallback` 分瀏覽器層與元件層，列跟這個做法的驗收層對應的那一個（例：`web/package.json`（加 `playwright-bdd`））。這是 ④ 一定會做的改動 —— 不列出來，使用者在 ③ 批准做法時不知道專案會多一個套件。

- **測試專案不只一個** → 寫成「`A.Tests` 或 `B.Tests`（③ 選）」，在「我建議」那節講哪一個、為什麼。放哪個由使用者挑。
- **一個都沒有** → 寫「新建測試專案」，代價算進「工」—— 那是結構決定，不是順手的事。
- `bdd` 有值（Reqnroll、SpecFlow、Cucumber、JBehave）→ 什麼都不加，④ 沿用既有的那一套。

## 回傳範本

```text
## 現況
{這塊現在怎麼做的，3-5 句。有哪些現成的擴充點。}

## 既有行為會變的
{改前（path:line）→ 改後，一項一行；只新增、既有行為都不變寫「無」}

## 資料來源
{一個來源一行，見[資料來源](sa-data-sources.md)；`current-state.md` 已經有這一節就寫「同 current-state.md」，再加上你補的那幾行；沒有這種資料寫「無」}

## 做法

### A) {一句話標題}
- 動到：改 {既有檔／表，具體列出來}；新增 {檔／表}
- 連帶影響：{會跟著變的既有功能與呼叫端（path）| 無（只查了直接呼叫端）}
- 既有測試：{要改期望值或刪掉的（path::名稱）| 無}
- 資料模型：{`data-model.md` 的「A)」| 無}
- 風險：{具體的失敗情境：什麼輸入／什麼狀態 → 什麼壞結果}
- 工：{大概幾個檔／幾個行為}
- 影響：資料={不動 | 動既有資料：什麼}　消費者={無 | 有：誰}
- 規範：符合 | 違反 {哪一條}，需要豁免 | 無
- 精度：{欄位型別與 scale}，與 spec 一致 | 衝突：{哪裡對不上} | 無

### B) ...

## 我建議
{哪一個，為什麼。沒有明顯較好的就說「沒有明顯較好的，差別在 X」。}
```

## 做法檢查

1. **`影響` 兩欄都必填，填的必須是你實際查到的值。** 這兩欄是 orchestrator 判斷「要不要停下來等使用者批准」的唯一依據 —— 留空或寫「待確認」等於讓那個判斷失效。查不出來就回 `blocked`。
   - `資料`：會不會動到**已存在的資料**或**正在跑的流量**？（migration／backfill／線上加索引／改認證授權）
   - `消費者`：有沒有**你控制不了的人**會看到差異？（對外 API／事件 schema／共用 library 介面／CLI 參數／給外部查的 view）**提供**契約才算，消費別人的不算。
2. **至少 2 個做法，至多 4 個。** 只想得到 1 個 → 那第 2 個是「不做／繞過」，把它的代價寫出來。

   想到 5 個以上 → **先用規則 3 篩一遍**（選 A 和選 B，要動的檔會不一樣嗎？）。多半會發現其中幾個是同一個做法的兩種寫法 —— 那才是這條上限真正在防的東西，合併掉就進到 4 個以內。

   **篩完仍然是 5 個以上，就回 5 個以上。** 硬合併會做出一個「A 的前半 ＋ B 的後半」的選項，而那個組合技術上不成立 —— 使用者會照著它做**不可逆的決定**，而且沒有人有機會發現它是拼出來的。多一個選項只是他多讀三行；一個不成立的選項是整條線做錯。這時要在「我建議」那節寫明**為什麼這幾個真的不能合併**。
3. **做法要真的不同。** 判準：**選 A 和選 B，要動的檔會不一樣嗎？** 不會就是同一個做法的兩種寫法。
4. **你回的是選項，不是設計稿。** 介面長什麼樣、函式怎麼切，是 `implementer` 的事。**資料表是例外** —— 一旦有資料就很難改，所以表格寫進 `data-model.md` 給使用者在 ③ 確認（見「資料表設計」）。
5. **講得出具體的檔名和表名。** 「需要修改相關的服務層」是沒有用的回答。「改」的那一半連同「連帶影響」「既有測試」就是 ③ 的改動範圍 —— 漏一項，④ 就在使用者沒批准的地方動手。
