# 單一團隊前後端試行

使用者指定一個團隊試行時適用。先記下團隊、已排程的需求、前後端 repo、驗收環境、允許的操作和比較基準。選一項同時需改 API 與 UI 的真實需求。

## 依風險選步驟

- **單端、需求明確且低風險的行為變更**可合併①需求釐清與②系統分析。照常執行③核准、BDD 驗收、測試與程式碼審查。純文字修正沿用原有例外。
- **一般功能**依原六步執行。
- **影響跨端契約、資料遷移、金額或授權**先在③審查規格草案。呼叫 `reviewer` 的 `spec` 模式，完成 `spec-review.md` 登記，把就緒結果與同一版草案併入③原本的核准。單行變更依影響判斷。交付前完成獨立程式碼審查。

## 共用決策

在決策來源需求的 `spec.md` 記錄決策 ID、版本、決定內容與影響範圍。各受影響需求記錄來源路徑、同一 ID 和採用版本。決策改動後依來源的影響範圍與各需求的引用逐項盤點，更新受影響規格、契約和驗收條件，再登記需要的重審與重核准。

## 驗收與觀察

1. 第③步確認真實 API 測試環境、UI 瀏覽器情境及可使用的測試資料。以核准的影響範圍測試。
2. 用瀏覽器執行一個主要情境，確認畫面結果及對應的真實 API 回應。交付記載測試指令、情境、前後端版本、結果和證據位置。依專案規範遮蔽個資與憑證。
3. 記下需求規模、從開始釐清到交付的耗時、使用者做決定的次數、以及前後端契約不一致造成的返工。用相同計法找同一團隊規模相近的已完成需求作比較。沒有可比案例時照實記錄觀察值。
4. 與試行團隊檢視證據和差異，決定是否擴大。試行交付包含真實 API 與 UI 情境，以及可解讀的觀察資料。
