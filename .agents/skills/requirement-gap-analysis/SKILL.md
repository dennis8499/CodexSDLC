# 需求缺口分析

用使用者的話與邏輯必然，試寫目標、角色、主流程（3–7 步、結束時的資料狀態）、所需資料和範圍。資料包含輸出欄位與計算輸入，由使用者輸入或功能本身產生的可略過來源檢查。orchestrator 以一般業務常識做 BA，repo 與 DB 的事實交給 SA。

## 選擇分支

| 判斷 | 下一步 |
| --- | --- |
| 主流程得猜好幾個業務事實，例如「退貨要做一下」 | 讀[需求很空](references/survey-draft.md)。先用 `sa-analyst` 的 `survey` 盤點，再起草給使用者確認 |
| 主流程清楚，但依賴另一套系統、第三方或外來檔案，來源沒說明 | 讀[資料來源不明](references/source-discovery.md)。先用 `survey` 對來源，整理仍需使用者回答的項目 |
| 主流程可寫，只缺一兩處或需要查例外 | 將缺處連同[九類缺口](references/gap-checklist.md)一起檢視。前端狀態與外部來源的業務決策也在那份清單 |
| 已經講清楚例外，或只是純技術改動 | 說「沒發現需求缺口」，進 ② |

本系統內可合理預期的資料來源交由 ② 對照。拿不準時，先當主流程可寫、資料在系統內。② 發現對不到來源或缺口太多時，會留下 `current-state.md` 交回。

## 實例與選項

- 只列必須由使用者決策且能舉出實例的缺口。用「我認為這裡可能還沒定」呈現推測。專業領域明說「這塊我的常識可能不準，你直接告訴我」。
- 問題與選項都用可辨識的具體值。數字取自使用者、附來源的 `current-state.md` 或明標的假設。倚賴尚未取得的領域事實時，先問該事實。真的是二選一時直接問，已給具體實例時沿用原話。
- 每題給 2–3 個具有不同結果的選項，建議需要最少額外前提的做法，理由寫一行。沒有明顯較好就說「三個差不多，差別在 X」。
- 用邊界值問時效、數量等門檻。精度題分開檢查捨入時點、方向、位數及負數。遇門檻或精度題讀[門檻與精度的實例](references/boundary-examples.md)。

例如，使用者給了出貨日與取消日，可問「訂單 8/10 出貨，客戶 8/12 按取消，會發生什麼？」建議擋下並提示改走退貨，因為只需維持已出貨狀態。其他選項要寫清楚是自動開退貨等收到貨才退款，或先進客服待審、核准才退。

## 提問與收斂

1. **先排依賴。** 先問答案可能讓其他缺口整批消失的那一層。例如已出貨不可取消時，這次不用決定取消後的退款或運費。
2. **同一輪最多 5 題。** 排完仍超過時，把全部缺口標題一行一項列出，請使用者切小範圍、指定先做的部分或分輪問。確認表單沿用 orchestrator 的「使用者互動」格式。
3. **先落決議，再找缺口。** 每輪答完把談定的實例及答案寫進 `bdd-docs/{feature-id}/spec.md` 的「需求決議」，供 Gherkin 的 `Given` 與 `Examples:` 取值。確認延後的缺口及答案新打開的缺口。兩者皆無才進 ②。
4. **缺口最多問 3 輪（含第一輪）。** 第 3 輪後仍有，再列出所有剩餘標題，請使用者選擇再問一輪、先進 ② 並標「待定」留到③，或切小範圍。起草主流程的輪數依[需求很空](references/survey-draft.md)處理。
