# spec.md 怎麼寫

**spec.md 是 ③ 拿去給使用者核准的那一份，也是 ④⑤ 唯一的驗收依據。** 下面每一條都有一個下游靠它：漏掉的話多半不會報錯，而是有人自己猜。

## 固定格式

- **第一行固定寫 `# {feature-id} —— {一句話，用他的話講這塊功能做什麼}`。** 下一個需求進門時靠這一行認出「這塊我們做過」（只 `grep -m1 '^#'` 這一行）—— **用他的話寫，不要翻成技術語言**。
- **同一塊功能的第二次迭代 → 在尾端新增一節 `## 迭代 N —— {一句話}`，前面幾次原樣保留。**（「輪」專指 ⑤ 的修正輪。）覆寫掉的 scenario 消失了，測試照樣全綠。這次的 Gherkin 區塊**只寫這次新增或修改的 scenario** —— 整份謄一遍等於邀請 ④ 整檔重寫。
- **驗收條件一律寫成 Gherkin，放在 ` ```gherkin ` 區塊裡**，它之後會**原封不動**變成 `.feature` 交給 QA —— 使用者確認的字，就是 QA 拿到的字。寫法見 skill `gherkin-authoring`。
- **Gherkin 區塊的第一行固定寫 `# feature-id: {feature-id}`**，擺在 `Feature:` 之上 —— 它跟著落進 `.feature`，②″ 靠它 grep 回原需求，`gherkin-check` 靠它找回這份 spec（少了這行它直接報錯）。
- **Gherkin 區塊底下多寫一行「驗收層」** —— 這幾條 scenario 繫結在哪個介面上（HTTP endpoint／application service／domain method／UI）。② 選定的做法已經決定了它；不寫的話 `implementer` 自己挑，**挑錯層正是假綠燈最常見的來源**。
- **驗收層是 UI（元件或瀏覽器）時，再寫一行「驗收方式」**，③ 跟使用者確認的就是「用什麼驗」：`驗收方式：{工具}｜{瀏覽器／project}｜{尺寸或輸入方式}｜後端：{真實／替身（依據）}`，四欄都要有，不適用寫 `—`。寫法與例子見 skill `gherkin-authoring` 的「前端 UI 驗收」。沒寫、少欄，`gherkin-check` 與 `delivery-check` 都不放行。
- **Scenario 的具體值直接取 ① 談定的實例**（「需求決議」裡的日期、金額、狀態、門檻的邊界值）—— 這一步是謄寫，不是發明。

## 改動範圍

**做法會改到既有的檔、表或行為（不只新增檔）就要寫**，放在做法底下。使用者在 ③ 核准的就是這一份：`implementer` 以它為邊界，`reviewer` 拿它對照 diff。

```text
## 改動範圍
- 既有行為：{改前 → 改後，一項一行；只新增、既有行為都不變寫「無」}
- 會改的既有檔／表：{path 或表名，具體列出；接線（DI 註冊、路由）也列}
- 連帶影響：{會跟著變的既有功能、呼叫端、報表、批次；沒有寫「無」}
- 既有測試：{要改期望值或刪掉的測試／scenario；沒有寫「無」}
- 不動：{這次明確不碰、但容易被順手改的；沒有就省略這一行}
```

- **內容取 `sa-analyst` 回傳裡選定做法的「動到」（改的那一半）、「連帶影響」「既有測試」，以及「既有行為會變的」那一節** —— 這一步是謄寫，不是重想。② 你自己查的就照你看過的檔寫，「連帶影響」一樣要查一次要改的方法有誰在呼叫（一次 grep）；會動 schema 就不是自己查得完的事，委派 `sa-analyst`。
- **使用者換了做法 → 整節換成那個做法的**，重問核准時連同新的範圍一起附上。
- **「既有行為」的改後值要對得上 Gherkin** —— 改後的值就是這次 scenario 的值；對不上就是其中一邊寫錯了。
- `implementer` 回報要改範圍外的既有東西、使用者同意了 → 補進這一節再交回。**這一節沒有的就是沒批准。**
- **迭代**：寫在那一次的 `## 迭代 N` 底下（標題降一級），只寫這次的。

## 資料表設計：只寫指向，不抄表格

做法會動 schema → 做法底下多一行：

```text
- 資料模型：`bdd-docs/{feature-id}/data-model.md` 的「A)」
```

表格本身留在 `data-model.md`（`sa-analyst` 寫，格式見 skill `er-modeling`），**不抄進 `spec.md`** —— 兩份會走鐘，而 `implementer` 與 `reviewer` 讀的是這一行指到的那一節。使用者在 ③ 改了欄位細節 → 改 `data-model.md` 那一節，不是在 `spec.md` 另寫一份差異。迭代時這一行寫在那一次的 `## 迭代 N` 底下，指到 `## 迭代 N：A)`。

## ④ 分次委派時：「切片與沿用」

③ 核准後依 `.codex/bdd-workflow/runbooks/review-evidence.md` 登記實作、測試與引用文件。把審查授權、風險決議、最小審核、切片與沿用及交付分別寫在各自的二級標題下。規格做法與驗收條件用核准版本的正文維護。

行為數 > 3、分次委派時，`spec.md` 多一節 `## 切片與沿用`，只有兩件事：

- **切法** —— 每片一行：這片是哪個行為、對應 ③ 的哪幾條 scenario。
- **沿用** —— 前面幾片建立、後續必須沿用的東西：step 詞彙、共用 fixture／helper 的 path、已建立的介面。**每片回來就更新，下一片委派前它必須是最新的** —— 不然下一片會另造一套，step 措辭分岔斷的是 QA 的 repo。進度不寫進去。

## 兩個例外

- **這次改動沒有可驗收的行為變更**（純重構、升套件、改設定）→ 驗收條件寫一行 DoD 就好；**「改動範圍」照寫**（「既有行為：無」）—— 重構改的全是既有檔，使用者最需要看的正是這一節。
- **這是 bug 修復**（走「症狀清楚、原因不明」那個分支）→ 寫一行 `回歸測試：{path}::{測試名}`，那個測試就是驗收條件。**②″ 查到原 spec 的話，把它的「驗收層」那一行抄過來**。`implementer` 回了修法 → 照上面寫「改動範圍」（修法的檔:行、改前 → 改後），③ 拿它問；還沒找到原因時先不寫，它改 production code 之前會先回來報修法，那時補上再問。
